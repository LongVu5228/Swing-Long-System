# HTF Pine Annotation Project — Master Context Handoff

## Purpose

This folder is a handoff package for Claude Code to build the **first version of a TradingView Pine Script annotation tool** for a systematic historical backtest of Qullamaggie-style High Tight Flag (HTF) setups.

The user already has a historical candidate list generated by a separate scanner/backtest pipeline. The Pine script is **not** responsible for discovering HTFs automatically.

Its job is to let the user perform **manual human visual annotation inside TradingView**, because the user trusts TradingView's chart rendering and wants to preserve discretionary chart-reading judgment.

The broader workflow is:

1. A historical scanner generates candidate tickers/dates.
2. The user opens each candidate in TradingView.
3. The user visually decides whether/where a legitimate HTF-style higher-low flag structure exists.
4. The Pine annotation script lets the user record:
   - flag start
   - setup-confirmed date
   - eventual/final flag end
   - one or more versioned resistance levels
   - optional setup type (normal higher-low flag vs shakeout/reclaim)
5. TradingView Chart Data Export is used to export Pine-generated numeric annotation fields.
6. A later local Python process will parse the exported CSV and append structured annotations into a master dataset.
7. A later backtester will compare actual entry rules using minute/daily data.

The script should be designed primarily for **fast manual annotation**, not automated setup classification.

---

# 1. Trading Method Context

The setup being researched is based on Qullamaggie's momentum breakout / high-tight-flag style.

The conceptual sequence is:

**big prior move -> pullback / sideways -> tightening -> higher lows / "surfing" behavior -> line of least resistance -> range breakout**

Important distinction:

- The **higher-low flag region is the setup structure**
- It is **not automatically an entry region**
- The trade should only become eligible after the human believes enough structure has formed
- Entry logic is tested later, e.g.:
  - 1-minute opening range high
  - 5-minute opening range high
  - 30-minute / 60-minute opening range high
  - prior-day high
  - flag/range high
  - manually drawn resistance break
  - first green daily close
  - combinations of the above

The annotation tool should therefore capture the **setup**, not hard-code the final trade-entry rule.

---

# 2. Human Discretion Is Deliberate

The user does **not** trust an automated HH/LH/HL pivot algorithm to define the visual flag.

Existing pivot logic is useful only for helping generate historical candidate lists.

The actual flag identification must remain **human visual judgment**.

The user wants to look at TradingView and say:

- this is where the pullback started
- this is where enough higher-low structure has formed
- this is now a legitimate flag
- this is the line of least resistance I care about

The Pine script should act as a **data-backed annotation layer**, not a classifier.

---

# 3. Definitions

## 3.1 flag_start

The first candle where the user believes the higher-low / flag structure begins developing.

This can only be known with hindsight and is mainly descriptive.

It does **not** make the setup actionable.

Example:

`flag_start = 2023-08-29`

---

## 3.2 setup_confirmed

The first date where, using only information available up to that candle, the user's trained eye says:

> "Enough of the higher-low box has formed that I now consider this a legitimate setup."

This is the most important timestamp.

The backtester must **not** test entries before `setup_confirmed`.

If a final visual box later extends further right, `setup_confirmed` must remain frozen at the earlier date.

Example:

- flag begins Aug 29
- enough structure exists by Sep 6
- setup is considered legitimate on Sep 6
- the box eventually extends through Sep 12

Store:

- `flag_start = Aug 29`
- `setup_confirmed = Sep 6`
- `final_flag_end = Sep 12`

The backtester may only evaluate entry logic after Sep 6.

This prevents look-ahead bias.

---

## 3.3 final_flag_end

The final right edge of the visual flag structure.

The user may extend this later while reviewing further candles.

Example:

A box is first considered valid on Sep 6, but keeps making higher lows until Sep 12.

`setup_confirmed` stays Sep 6.
`final_flag_end` becomes Sep 12.

The script should make it easy to update the end date without changing the confirmation date.

---

## 3.4 resistance

Resistance / "line of least resistance" is **discretionary**.

The user does not yet want to assume it is simply:

> highest high of the completed flag region

That hypothesis may later be tested, but for now resistance is manually chosen.

Resistance is conceptually the price level that matters once a valid higher-low flag exists.

---

# 4. Resistance Must Be Versioned Over Time

This is critical.

A single flag may have multiple resistance levels over time.

Example:

- Setup confirmed Sep 6
- Resistance #1 = $50 beginning Sep 6
- Price never actually touches/crosses $50
- Flag keeps developing
- On Sep 12 user moves resistance to $53
- Resistance #2 becomes active beginning Sep 12

The backtester must know:

- Sep 6 through Sep 11: active resistance was $50
- Sep 12 onward: active resistance was $53

Therefore, do not store only the final resistance level.

Each resistance needs at least:

- resistance number / ID
- effective date
- price

Example structured representation:

| resistance_id | effective_date | price |
|---|---|---:|
| 1 | 2023-09-06 | 50.00 |
| 2 | 2023-09-12 | 53.00 |

---

# 5. What Counts as "Resistance Touched"

The user explicitly defined:

If price merely trades through or touches the resistance intraday, that counts as the resistance being touched/triggered as a **market event**.

However:

**Resistance touched != trade entry**

The entry rule is a separate later backtest question.

Example:

- Resistance = $50
- Stock trades to $50.15 intraday
- That means resistance was touched/crossed
- A later-tested 5-minute ORH rule might still not fill
- That is fine

The annotation script does not need to decide whether the trade was entered.

A later backtester will handle that.

---

# 6. Multiple Flag Occurrences Per Ticker

A single ticker can have many separate flag structures.

Typical:
- 1–4 flags on a long chart

Possible:
- up to about 10

Example:

A stock may:
1. form higher lows
2. fail
3. later form another higher-low flag one week later

Those are separate setup occurrences.

Do not overwrite Flag #1 when Flag #2 forms.

The script should support **at least 10 separate flag slots**.

---

# 7. Green vs Red Setup Types

The user is currently manually marking:

## Green boxes
Normal higher-low / tightening / surfing-type flag structure.

Suggested type label:

`HL_FLAG`

## Red boxes
A different phenomenon:

- stock is pulling back
- makes a lower low / looks like it is failing
- then produces a large green reclaim / shakeout-like move
- may proceed higher afterward

Suggested type label:

`SHAKEOUT_RECLAIM`

The user originally planned to finish green boxes first and study red boxes later.

However, once annotation becomes fast, it is desirable to preserve both types during the same review session.

Do not combine their backtests automatically.

Store them as different `setup_type` values.

---

# 8. Why TradingView Must Remain the Visual Interface

The user strongly prefers TradingView for actual discretionary judgment.

Reason:
- familiar GUI
- trusted daily chart appearance
- manually trained visual eye
- concern that a custom local chart renderer will not feel identical enough to TradingView

Therefore:

The preferred architecture is **TradingView-native visual annotation via Pine**, then export structured values.

A local companion application may later be used only for ingestion/automation, not primary chart judgment.

---

# 9. Why Normal TradingView Rectangles Are Not Enough

The user's ideal workflow would be:

> manually draw TradingView rectangles -> export all rectangle dates to CSV

But TradingView's normal manually drawn UI rectangles are not directly available to Pine for structured export.

So the workaround is:

Use **interactive Pine inputs** that act like data-backed chart annotations.

The Pine script should let the user place time and price values interactively while staying inside TradingView.

---

# 10. Pine Script Concept

Build a TradingView indicator tentatively named:

**HTF Manual Flag Recorder**

It should let the user annotate each flag with interactive inputs.

The script should:

- render the annotation visually on the TradingView chart
- preserve its timestamps/prices numerically
- output numeric series that can appear in Chart Data Export
- avoid trying to classify the chart automatically

---

# 11. Desired Flag Slot Structure

For each flag slot, ideally support:

- Enabled / Active checkbox
- Setup Type:
  - HL_FLAG
  - SHAKEOUT_RECLAIM
- flag_start
- setup_confirmed
- final_flag_end
- multiple resistance versions

Minimum target:
- 10 flag slots

Suggested starting target for V1:
- 10 flags
- perhaps 3 resistance versions per flag

If Pine input limitations or UI clutter make that too painful, prioritize:
- 10 flags
- 2 resistance versions each
- then expand later

---

# 12. Interactive Input Behavior

The user should be able to select or drag dates on the actual TradingView chart.

Pine features likely useful:

- `input.time()`
- `input.price()`
- `confirm=true`
- grouping / inline UI organization
- boxes
- lines
- labels

Ideal process for a normal green flag:

1. Enable Flag #1
2. Select type `HL_FLAG`
3. Click / set flag start
4. Click / set setup-confirmed date
5. Click / set current/final end
6. Set Resistance #1 effective date
7. Set Resistance #1 price
8. If needed later, set Resistance #2 effective date and price
9. Visually render box and resistance line(s)

The user may later extend `final_flag_end`.

The script must not automatically alter `setup_confirmed` when end changes.

---

# 13. Visual Rendering Goals

The script should visually resemble the user's current manual annotation workflow.

Preferred:

## HL_FLAG
Draw a green-like flag region box.

## SHAKEOUT_RECLAIM
Draw a red-like box.

If custom coloring adds unnecessary complexity, keep V1 simple, but distinct setup types should be visually distinguishable.

The script should draw:

- box from flag_start -> final_flag_end
- visual marker for setup_confirmed
- horizontal resistance line starting from its effective date
- resistance version #2 / #3 if provided

Avoid clutter.

---

# 14. Resistance Visual Logic

Each resistance version should ideally have:

- effective date
- price
- horizontal line beginning at that effective date

If Resistance #2 is introduced later:

- Resistance #1 should remain historically visible or at least remain numerically preserved
- Resistance #2 becomes the current level

Do not overwrite Resistance #1.

---

# 15. Export Strategy

The user has TradingView access sufficient for Chart Data Export.

The planned export path is:

TradingView -> Export Chart Data -> CSV

The Pine script should expose machine-readable annotation values through plots/series so they are included in CSV export.

Important:

The export is expected to be **one export per ticker/chart**, not one export per flag.

If ACAD has 4 flags and multiple resistance levels, all annotations should be captured in the same ticker export.

---

# 16. Export Design Requirements

The local parser should eventually be able to reconstruct structured events from exported chart data.

Possible numeric output columns:

For each Flag N:

- `F1_ENABLED`
- `F1_TYPE`
- `F1_START_TS`
- `F1_CONFIRMED_TS`
- `F1_END_TS`

Resistance versions:

- `F1_R1_EFFECTIVE_TS`
- `F1_R1_PRICE`
- `F1_R2_EFFECTIVE_TS`
- `F1_R2_PRICE`
- `F1_R3_EFFECTIVE_TS`
- `F1_R3_PRICE`

Repeat for Flag 2 ... Flag 10.

Because plots are time series, one practical approach is to output the same annotation scalar on every visible bar.

The later parser can simply take the last non-null value for each field.

If TradingView CSV behavior makes timestamps awkward, use Unix epoch milliseconds or another numeric date representation.

The exact encoding can be decided during implementation.

---

# 17. Setup Type Numeric Encoding

Suggested:

- 0 = unused
- 1 = HL_FLAG
- 2 = SHAKEOUT_RECLAIM

Keep this documented for the parser.

---

# 18. Key Backtest Rule

No entry simulation before `setup_confirmed`.

This is non-negotiable.

The visual region may begin earlier, but the setup is not considered knowable/valid until the human says enough structure exists.

Example:

Final box:
`8/29 -> 9/12`

Human says setup first became valid:
`9/6`

Backtester starts evaluating entry triggers only from:
`9/7` onward, or after the Sep 6 close depending on the chosen entry rule.

Exact same-day vs next-day timing depends on later entry-rule semantics.

---

# 19. Resistance Timing Rule

Resistance must be point-in-time aware.

Example:

R1:
- effective Sep 6
- $50

R2:
- effective Sep 12
- $53

The backtester must never use R2 before Sep 12.

This prevents resistance hindsight leakage.

---

# 20. Existing Manual Excel Convention

The user currently has a `Flag Days` text column.

Example:

`1/4-2/5, 3/4-4/15`

Meaning:

- one higher-low flag region from Jan 4 through Feb 5
- another separate region from Mar 4 through Apr 15

This is already storing ranges, not every individual daily candle.

The Pine/export workflow should eventually replace manual typing of this field.

A later program can reconstruct the readable text cell from structured annotations.

---

# 21. Intended Structured Dataset

Long-term preferred storage is normalized, not one giant Excel text cell.

Suggested table:

| ticker | parent_htf_row_id | flag_id | setup_type | flag_start | setup_confirmed | final_flag_end |
|---|---|---:|---|---|---|---|

Separate resistance table:

| ticker | parent_htf_row_id | flag_id | resistance_id | effective_date | resistance_price |
|---|---|---:|---:|---|---:|

Or one flattened table if simpler for V1.

The important thing is:
- multiple flags
- multiple resistance versions
- point-in-time dates

---

# 22. Local Export Automation — Later Phase

The user correctly noticed a problem:

If there are ~2,000 tickers, native Chart Data Export may imply ~2,000 CSV downloads.

This is acceptable computationally but annoying manually.

Later plan:

1. Keep TradingView/Pine as annotation interface.
2. Use a browser macro / AutoHotkey / automation shortcut to perform Chart Data Export.
3. A Python folder watcher monitors the Downloads folder.
4. When a new TradingView CSV appears:
   - detect ticker
   - parse HTF annotation columns
   - append to master annotations dataset
   - archive/delete raw export
   - confirm saved
5. User moves to next ticker.

This later automation is **not required for Pine V1**.

Pine V1 should focus on:
- annotation UX
- correct point-in-time fields
- correct CSV-exportable numeric outputs

---

# 23. What NOT to Build in V1

Do not:

- automatically identify higher lows
- automatically classify a valid HTF
- automatically pick final resistance
- build the actual trade backtester
- build minute-entry logic
- build a custom replacement for TradingView
- use current manual HH/LH pivots as authoritative annotation
- infer a setup before the human marks it

---

# 24. V1 Success Criteria

V1 is successful if the user can open a ticker in TradingView and:

1. Mark a flag start
2. Mark setup-confirmed date
3. Mark/extend final flag end
4. Add at least one discretionary resistance level
5. Add later resistance versions without deleting history
6. Repeat for several separate flags on the same ticker
7. Export Chart Data
8. See annotation fields clearly represented in the CSV
9. Reopen/change the inputs without corrupting earlier date semantics

---

# 25. Important User Preferences

- Keep the tool practical and fast.
- Human eyes decide the setup.
- TradingView remains visual source of truth.
- Avoid look-ahead bias.
- Do not over-engineer V1.
- Make the UI tolerable even with many flag slots.
- User may need up to 10 flags on one ticker.
- Resistance is discretionary and can change over time.
- Resistance touch is a market fact; trade trigger is a separate later test.
- The user is comfortable iterating with Claude Code.

Do not prematurely optimize.

The ideal implementation sequence:

### Phase 1
One-flag proof of concept

### Phase 2
Validate TradingView CSV export behavior

Expand to 10 flags

### Phase 4
Add setup types and more resistance slots if needed
